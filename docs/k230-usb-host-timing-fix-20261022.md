# K230 USB 主机时序修复及 SRAM 诊断

## 当前结论

2026-10-22，USB 主机候选的真实 I/O 约束时序已收敛；最终报告 setup0/hold0，
最差 setup +1.481ns、hold +0.325ns。7 项 Python/Amaranth 测试通过，120.582秒。
另外通过实际手势解析/UART报文/周期健康报告/PLL失锁复位 RTL 测试，以及高云
rPLL 官方模型的频率、相位和占空比测试。没有宣称 UTMI 仿真覆盖了真实 USB 电气层。

FPGA 已进行独立 SRAM 诊断下载，未写 Flash。第一次下载读回 E024，退出码0，
但工具报 User code mismatch，原始警告保留；随后从 COM13 只读录到99字节，
得到11帧不重叠且 XOR 正确的健康报文。这证明新诊断逻辑和 PHY 来源时钟正在运行，
不证明 K230 已经枚举。UART未发送命令，DTR/RTS关闭。

## 关键修复

1. PHY RESETB低有效，PLL锁定后再两级释放USB复位；失锁立即复位主机。
2. 从普通引脚进入的60MHz时钟有约4–6ns片内延迟。改用rPLL的315°相位输出，
   即模周期的提前45°。官方模型实测周期16.667ns、相位14.585ns、高电平8.334ns。
3. UTMI发送队列使用4深度缓冲，显式存储包结束标记，切断NXT/DIR直通到上游FIFO
   计数器的长路径，避免长时间背压后合并数据包。
4. LUNA命令数据译码拆出data_idle：保留寄存器访问优先级，消除DIR到命令数据的
   不必要门控。DIR高时引脚三态；握手、FSM、STP不变。初稿在完整总线对照测试
   中失败，修复后6000周期完整对照及3000周期发送器对照均通过。

## 相位与采样边沿约束说明

PLL输出定义为正相位315°（14.584ns），片内时钟延迟约4.21ns后，其正标号边沿
位于18.79ns，已经越过16.667ns的PHY边沿；这个边沿产生的数据由33.334ns的
PHY边沿采样。因此只对该PLL时钟到ULPI数据/STP输出配对使用setup2/hold1。
这等价于物理周期内约+2.13ns的核心采样边沿，对16.667ns的下一个PHY边沿输出。
建立时间检查保留数据手册5ns与板级0.5ns预算；hold配对检查前一个PHY边沿。
内部主机路径没有multicycle，输入与DIR到引脚组合路径也没有放宽。

Gowin不接受负数波形；直接设置-45°的尝试被TA1072拒绝，已撤回，采用上述正相位
与实际采样周期对应的约束。另一个27MHz域仅生成上电复位，通过两级同步释放；
它与USB域为异步域。没有把USB数据路径设置为false path。

板级0.5ns预算仍为假设而非实测；时序通过不替代温度、电流或USB眼图测试。
过去发热根因未解决，hardware-hold.json默认限制保留。此次为用户明确授权的
固定候选SRAM诊断，且用户在下载前确认“不烫、K230未接”。

## 后续联调

健康报文flags bit1表示CDC已配置；bit0表示有效手势。当前K230未连接，flags应为0。
接K230后先确认枚举/配置，再确认它发出12字节二进制手势帧。现有预览打印文本
不能充当二进制发送程序；置信度门限60不变。此诊断版没有音频合成与OLED功能。
旧E023乐器程序仍保留在Flash，断电重启或RCFG会恢复旧程序并丢失本次诊断版。
